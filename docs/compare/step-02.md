# step-02 与 PiG 的差异清单

对应提交：`step-02`（多轮对话循环）。

## 文件对应

| mypi | PiG | 说明 |
| --- | --- | --- |
| `cmd/mypi/cli.go` 的 `askRepeatedly` | `coding/cli/main.go` 的交互入口 + `internal/codingagent/interactive.go` | 我们只有最朴素的读行循环 |
| `agent/agent.go` 的 `Run` | `agent/agent_loop.go` 的 `loop` / `runTurn` | 我们只有一层，PiG 有两层 |

## 已经照着做的

1. **一条循环两种用法**：单次提问和交互模式都调用同一个 `Agent.Run`，区别只在输入从哪来。
2. **每轮重发完整历史**：模型无状态这件事没有例外，第二轮请求里就是三条消息。
3. **失败不污染历史**：某一轮 provider 报错时，那半截问题不会留在上下文里。测试 `TestReplKeepsGoingAfterProviderError` 专门盯这点。

## 故意不一样的地方

### 1. 历史放在 CLI 里，Agent 是无状态的

我们是 `Run(ctx, history) []Message`：谁调用谁持有历史，Agent 每次都从头拿到尾。

PiG 的 `loopRun` 自己持有 `r.context`，每次请求从里面取；外层 `loop()` 还要处理 steering（用户中途插话）和 follow-up（一轮结束后追加的问题）。

**为什么先这样**：无状态的 `Run` 最好测也最好读——给一段历史，拿回一段历史，没有隐藏状态。有状态的好处（流式过程中插话、工具执行到一半追加指令）要到票 03 之后才用得上。

### 2. 只有一层循环

PiG 是两层：外层管"还有没有下一轮对话"，内层管"这一轮里还有没有工具调用"。我们现在只有最朴素的一层：读一行、问一次、打印。

**什么时候变**：票 03 引入工具调用后，内层必须出现（一次响应里可能有工具调用，执行完要再问一次）；外层到那时仍然可以保持"读一行问一次"。

### 3. 错误不写进历史

PiG 在 provider 出错时会构造一条 `AssistantMessage{StopReason: error}` 放进上下文，让 UI 和后续逻辑都能看到"这里曾经失败过"。

我们只把错误打到 stderr，历史保持不变。

**代价**：用户看不到"上一轮失败了"的痕迹；如果以后要显示重试提示，得自己补。
**好处**：上下文里永远不会出现半条错误消息，模型不会去评论自己的错误。

**什么时候重新考虑**：票 04 接真 provider，遇到限流/超时时可能需要把这条件记下来给人看（但不一定塞回上下文）。届时再决定。

### 4. 没有 steering / follow-up

PiG 支持在模型生成过程中插话，也支持一轮结束后自动追加问题。我们的输入循环是严格一问一答，模型说话时不能输入。

**为什么**：这需要把"读输入"和"读事件"放进同一个 select（也就是 PiG 的单线程事件循环），属于票 11 的 TUI 才需要解决的问题。
